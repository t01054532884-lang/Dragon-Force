## 2. 재사용 요소
- 저장·지급 규칙이 순수 함수(`Progress.ts`·`Mailbox.ts`)라 서버 Functions로 거의 그대로 옮김. 모든 지급에 작업 ID(`txId`) 이미 사용.
- 계정 창구 `src/systems/Account.ts`(AccountProvider) — 지금은 게스트만. Apple 연결을 여기에 붙임.
- 캠페인(운영자 보상) 구조 `src/data/campaigns.ts`: 대상·기간·계정당 1회 — 서버 `campaigns/{id}`로 같은 모양.
- 저장 이전·보정 `sanitize`(구버전 저장 자동 변환, 손상 백업).

## 3. 수정 화면·데이터(서버 붙일 때)
- 설정: 계정 칸(Apple 연결·로그아웃·**계정 삭제**), 저장 충돌 선택 창("이 기기 / 서버").
- 상점: 루비 결제 상품·구매 복원·결제 전 안내.
- 저장 데이터: `users/{uid}` = 지금 `PlayerProgress`(데이터 버전 포함) + 유료/무료 루비 분리 장부.

## 4. 서버 작업(단계별)
| 단계 | 내용 | 작업량(대략) |
|---|---|---|
| 1 | Firebase Auth 익명 로그인 + Firestore 저장 동기화(첫 로그인 기기 저장 1회 업로드, 서버에 있으면 선택 창, 실패 시 기기 저장 유지·재시도) | 3~4일 |
| 2 | Sign in with Apple 연결(같은 UID 유지), 로그아웃, 앱 안 계정 삭제 | 2~3일 |
| 3 | Cloud Functions: 선물 수령·상자·정산·결제 지급을 서버가 처리(재화 필드는 앱이 직접 못 씀), RevenueCat 확인 거래만 루비 지급, 원격 설정 | 5~7일 |
| 4 | 운영 도구(관리자 웹·별도 인증·감사 로그)로 보상 발송 | 3~5일 |
- 오프라인: 기기 저장으로 플레이 → 연결되면 업로드(재화 변경은 서버 거래만 인정). 점검: 원격 설정 `maintenance` 값 → 로비 안내.
- 개인정보: UID와 Apple 연결 식별자만. 토큰·이메일 로그 금지. 개인정보처리방침 개정.
- 유지비: Firebase Blaze(초기 규모면 무료 한도 안 예상, 예산 알림), RevenueCat 월 매출 $2,500까지 무료.

## 5. 위험 요소
- 서버 붙이면 지금 기기 계산 재화와 서버 장부가 갈라질 수 있음 → 2단계까지는 "저장 백업", 3단계부터 재화 서버 확정.
- 결제 지급 실패·중복·환불 처리(시험 목록 7개, `MONETIZATION_PLAN.md`)를 다 통과하기 전엔 결제 출시 미룸.
- 애플 심사: 로그인 넣으면 계정 삭제 필수(5.1.1(v)).
- 서류 마감(11/24) 전에는 1단계까지가 현실적.

## 6. 확인이 필요한 결정
1. 5장 로그인: 11/20 결정(Apple + 게스트) 그대로인지, Google도 첫 출시에 넣을지.
2. 첫 App Store 제출에 서버(1~2단계)를 넣을지, 서버 없이 먼저 내고 업데이트로 붙일지.
3. 중복 계정 병합: 자동 합산 금지·선택 창 방식 동의 여부.
4. 룬·룬 상자·골드 구매 수치(AI 1차안) 확정.
