## 1\. 로그인은 어떤 방식이 좋을까?

나는 처음부터 회원가입을 강요하는 방식은 추천하지 않아. 게임을 처음 켰을 때부터 이메일과 비밀번호를 입력하라고 하면 플레이하기 전에 이탈할 수 있기 때문이야.

### 추천하는 로그인 3종

| 방식 | 적용 | 설명 |
|--------|--------|--------|
| 게스트 플레이 | 기본 제공 | 로그인하지 않고 즉시 플레이 |
| Apple 로그인 | iOS 우선 | Apple 계정에 게임 데이터 연결 |
| Google 로그인 | 제공 권장 | iOS·Android 계정 연결에 활용 |

이메일·비밀번호 직접 회원가입, 카카오·네이버 로그인은 초기에는 제외하자. 향후 국내 유저 반응에 따라 추가할 수 있어.

Apple의 현재 심사 규정은 소셜 로그인에 대한 동등한 개인정보 보호 로그인 옵션을 요구하며, 계정 생성 기능이 있으면 앱 안에서 계정 삭제도 제공하도록 하고 있어. Apple 로그인과 Google 로그인을 함께 제공하는 구성은 이 요구사항을 충족하기 쉬운 선택이야. 〔출처: 이전 채팅의 인용 자료 참조〕

Firebase는 인증과 Firestore 보안 규칙, 서버 함수, 푸시 알림을 연결할 수 있어. 특히 보상을 지급하는 함수에서 사용자 인증을 확인하고, Firestore 트랜잭션으로 중복 수령을 방지할 수 있다는 장점이 있어. 〔출처: 이전 채팅의 인용 자료 참조〕

## 3\. 어떤 데이터를 받아서 관리할까?

게임 운영에 필요한 정보만 수집하자. 전화번호, 집 주소, 생년월일, 실명은 현재 Dragon Force에 필요하지 않아.

### 유저별 저장 데이터 설계

| 구분 | 저장 항목 | 활용 |
|--------|--------|--------|
| 계정 | 고유 UID, 로그인 방식, 생성일 | 유저 구분·계정 복구 |
| 프로필 | 닉네임, 대표 드래곤 | 로비·운영자 조회 |
| 재화 | 골드, 루비, 소환권 | 상점·보상 지급 |
| 행동력 | 현재 행동력, 마지막 회복 시각 | 30분 자동 회복 |
| 드래곤 | 보유 종류, Lv.1\~40, 별, 카드·정수·조각 | 성장·수집 |
| 장비 | 보유 장비, 강화 레벨, 장착 상태 | 장비 관리 |
| 스킬 | 해금한 특수 스킬, 조각, 장착 상태 | 스킬 관리 |
| 연구소 | 능력별 강화 단계 | 영구 성장 |
| 스테이지 | 난이도별 클리어 기록, 최초 클리어 보상 | 진행도·선물 |
| 소환 | 뽑기 횟수, 천장 카운터, 수령 기록 | 소환·확률 보장 |
| 이벤트 | 출석, 룰렛, 누적 보상 | 이벤트 보상 |
| 선물함 | 미수령·수령 완료 선물, 수령일 | 보상 관리 |
| 기타 | 저장 버전, 마지막 로그인, 앱 버전 | 업데이트·오류 대응 |

사용자 이메일은 계정 연동에 필요할 때만 인증 제공자가 전달하는 범위에서 처리하고, 게임 운영에 불필요하다면 별도로 복사해 보관하지 않아도 돼.

Apple은 App Store Connect에 앱에서 수집하는 데이터와 사용 목적을 정확히 신고하도록 요구해. 게임 진행 기록이나 사용자 식별자, 진단 정보도 실제 수집 여부에 따라 검토해야 해. 〔출처: 이전 채팅의 인용 자료 참조〕

### 선물함 상세 규칙

| 기능 | 구현 규칙 |
|--------|--------|
| 미수령 개수 표시 | 로비 선물함 아이콘 위 빨간 숫자 |
| 개별 수령 | 선물 하나씩 선택 |
| 일괄 수령 | 수령 가능한 선물을 한 번에 처리 |
| 수령 완료 | 즉시 미수령 목록에서 제거 |
| 공간 부족 | 행동력 상한 때문에 못 받는 선물은 유지 |
| 선물 정렬 | 미수령 우선, 오래된 순 |
| 수령 내역 | 최근 수령 이력 확인 |
| 만료 | 기본 운영자 선물은 30일, 스테이지 최초 클리어 보상은 만료 없음 |
| 수령 중 오류 | 중복 지급 없이 재시도 가능 |

### 행동력 선물 처리 예시

현재 행동력은 25/40이고, 선물함에 행동력 20개가 두 개 있다면?

- 행동력 선물은 둘 다 현재 수령 불가
- 루비나 골드 선물은 정상적으로 수령 가능
- 일괄 수령 시 행동력 선물 두 개는 남겨둠
- 행동력을 소비해 20/40 이하가 되면 행동력 선물 1개를 수령할 수 있음

이렇게 처리하면 사용자가 일괄 수령을 눌렀다고 행동력 선물이 사라지는 일이 없어.

**서버에서는 일괄 수령 전체를 하나의 검증된 작업으로 처리하고, 일부만 수령 가능할 때 어떤 항목을 수령했는지 정확히 응답**해야 해. 보상이 많으면 작은 묶음으로 나누어 처리하되 중복되지 않아야 해.

## 전체 유저 보상 발송 구조

전체 유저가 많아지면 유저 수만큼 선물 문서를 즉시 생성하는 방식은 비용이 커질 수 있어.

그래서 다음 구조를 추천해.

**운영자: 전체 루비 1,000개 발송**

**서버: 보상 캠페인 1건 등록**

campaignId, 대상 조건, 보상, 유효기간

**유저 접속 시 선물함에 표시**

전체 보상과 개인 보상 통합 조회

**유저 수령 요청 → 서버 검증 → 재화 지급**

이 방식은 서버에 전체 보상 캠페인을 한 번 등록하고, **각 이용자가 수령할 때 캠페인 ID와 이용자 UID 조합으로 수령 여부를 기록**하는 방식이야.

중요한 기술 조건은 다음과 같아.

- 캠페인 발송 대상은 발송 시점에 확정하거나, 대상 조건을 변경 불가능한 형태로 저장
- 전체 대상이 '발송 당시 가입자'인지 '기간 내 신규 가입자 포함'인지 설정
- 한 이용자가 여러 기기로 동시에 수령해도 1회만 지급
- 재화 지급과 수령 기록을 하나의 원자적 트랜잭션으로 처리
- 서버가 중복 수령을 거부
- 캠페인 취소 이후 이미 수령한 보상은 임의 회수하지 않음

**전체 유저에게 루비를 지급하는 건 푸시 알림으로 하는 게 아니야.** 서버의 보상 기록이 실제 지급 근거이고, 푸시는 '선물이 도착했다'는 알림만 담당하도록 해야 해.

Firebase Cloud Messaging은 여러 앱 인스턴스에 토픽 메시지를 보낼 수 있지만, 기기나 알림 설정에 따라 사용자에게 표시되지 않을 수 있으므로 게임 재화 지급 자체를 푸시에 의존하면 안 돼. 〔출처: 이전 채팅의 인용 자료 참조〕

# 6\. 게임 업데이트도 서버에서 관리할 수 있을까?

가능해. 다만 **모든 업데이트를 서버에서 하는 것은 아니야.**

| 변경사항 | 서버에서 처리 가능? |
|--------|--------|
| 전체 유저 루비 지급 | 가능 |
| 점검 보상 발송 | 가능 |
| 출석 이벤트 보상량 변경 | 가능, 미리 지원한 설정 범위에서 |
| 이벤트 시작·종료 | 가능 |
| 골드 보상 배율 조정 | 가능, 서버 설정을 읽도록 구현한 경우 |
| 점검 공지 표시 | 가능 |
| 신규 드래곤 이미지 추가 | 앱 자산 구조에 따라 앱 업데이트 필요 |
| 새로운 전투 시스템 추가 | 앱 업데이트 필요 |
| 로그인 기능 추가 | 앱 업데이트 필요 |
| 보안·게임 코드 버그 수정 | 일반적으로 앱 업데이트 필요 |

게임의 새로운 기능과 이미지를 추가하려면 클라이언트 업데이트가 필요할 수 있지만, 기존에 구현해 둔 보상 종류나 이벤트 설정을 바꾸는 것은 서버에서 관리할 수 있어.

### 원격 운영 설정 예시

```json
{
  "configVersion": 3,
  "minimumSupportedVersion": "1.0.0",
  "maintenance": false,
  "energy": {
    "max": 40,
    "regenMinutes": 30,
    "stageEntryCost": 5
  },
  "christmasEvent": {
    "enabled": true,
    "startAt": "2026-12-01T00:00:00+09:00",
    "endAt": "2027-01-01T00:00:00+09:00"
  }
}
```

이런 방식으로 설정을 관리하되 이미 시작한 전투의 몬스터 HP나 보상을 서버에서 갑자기 바꾸면 안 돼. **전투 시작 시 설정 버전을 고정**하고, 보상은 해당 버전의 서버 규칙을 기준으로 검증하도록 설계하는 게 좋아.

# 7\. 로그인 및 기존 저장 데이터 이전

지금 Dragon Force에서 특히 중요한 건 **이미 게임을 플레이한 유저의 기존 저장 데이터를 잃지 않는 것**이야.

따라서 앱에 처음 서버를 연결하는 과정에서 기존 로컬 저장 데이터의 이전 절차를 반드시 넣어야 해.

## 최초 업데이트 시 동작

1. **기존 저장 데이터 확인**
   
   기기에 남아 있는 드래곤, 장비, 루비, 골드, 스테이지 기록 등을 읽어.
2. **계정 생성 또는 로그인**
   
   게스트 익명 UID를 생성하거나 Apple·Google 계정으로 로그인해.
3. **서버 저장 여부 확인**
   
   새 계정인지 기존 클라우드 데이터가 있는 계정인지 확인해.
4. **기존 데이터 안전 이전**
   
   새 계정이면 로컬 데이터를 검증한 뒤 서버에 한 번만 가져오고, 기존 서버 계정이 있으면 자동 덮어쓰기하지 않아.
5. **이전 결과 확인**
   
   드래곤·장비·재화·스테이지·이벤트·선물함 데이터가 정상인지 확인하고, 성공 기록을 저장해.

**주의\:** 예전 로컬 저장값은 사용자가 수정할 수 있으므로, 서버에서는 무조건 신뢰하면 안 돼. 특히 루비, 소환권, 정수 등 경제 재화는 검증 범위를 정해야 해.

초기 이전은 한 번만 허용하고, 이후에는 서버 기록을 기준으로 운영하는 게 좋아.

### 기기 변경과 계정 연동

| 상황 | 처리 방식 |
|--------|--------|
| 게스트로 계속 플레이 | 같은 앱 데이터가 유지되는 동안 이어서 플레이 |
| 게스트 → Apple 연동 | 기존 UID와 게임 데이터 유지 |
| 게스트 → Google 연동 | 기존 UID와 게임 데이터 유지 |
| 새 기기에서 동일 계정 로그인 | 클라우드 데이터 복원 |
| 미연동 게스트의 앱 데이터 삭제 | 복구가 보장되지 않음 |
| 다른 계정에 이미 데이터가 있음 | 자동 병합 금지, 계정 선택 및 확인 과정 필요 |
| 로그아웃 | 서버 데이터 유지, 다른 계정 데이터와 혼합 금지 |

Firebase에서는 익명 계정을 기존 로그인 자격 증명과 연결할 수 있지만, 이미 다른 UID에 연결된 로그인 제공자를 연결하는 경우 충돌 처리가 필요해. 재화와 드래곤 데이터를 자동 합산하면 복제 문제가 생길 수 있으므로 **계정 병합은 초기에는 지원하지 않는 것**이 안전해. 〔출처: 이전 채팅의 인용 자료 참조〕

# 8\. 재화 조작과 중복 보상을 어떻게 막을까?

여기는 출시 전에 꼭 고려해야 해.

기존처럼 모든 재화를 로컬 저장소에만 저장하면 사용자가 저장값을 수정해 루비를 크게 늘릴 가능성이 있어.

### 권한을 분리하자

| 작업 | 게임 앱 | 서버 |
|--------|--------|--------|
| 현재 루비 확인 | 조회 | 실제 잔액 보관 |
| 루비 150개로 상자 구매 | 요청 | 잔액 확인·차감·추첨·지급 |
| 드래곤 성장 | 요청 | 재료·골드 차감 및 레벨 변경 |
| 행동력 자동 회복 | 예상값 표시 | 최종 회복량 검증 |
| 선물 수령 | 요청 | 수령 가능 여부 확인·보상 지급 |
| 출석체크 수령 | 요청 | 날짜·중복 여부 검증 |
| 룰렛 돌리기 | 요청 | 참여 횟수 확인·확률 추첨 |
| 스테이지 클리어 보상 | 전투 결과 전송 | 완료 여부 검증·보상 지급 |

특히 **룰렛 당첨 결과를 클라이언트가 직접 정하면 안 돼.** 결과 추첨과 보상 지급을 서버에서 처리하는 것이 핵심이야.

문제는 현재 Dragon Force가 클라이언트에서 전투를 실행하는 구조라는 점이야. 서버가 없는 상태에서 단순히 `clear: true`라는 데이터만 받아 보상을 지급하면 누구나 조작할 수 있거든.

그래서 전투 보상 검증은 다음과 같이 단계적으로 개발하는 걸 추천해.

- **1차\:** 전투 시작 시 서버에서 sessionId·시작 시각·스테이지·설정 버전을 발급하고 행동력 차감
- **2차\:** 전투 종료 시 해당 세션을 1회만 정산하고, 최소 진행시간 및 결과의 기본 타당성을 검증
- **3차\:** 비정상적으로 많은 보상, 지나치게 빠른 클리어, 반복 수령 등을 탐지
- **장기\:** 중요한 전투 결과에 대한 서버 검증이나 결정적 시뮬레이션 재현 강화

1\~3차만으로 조작을 완전히 차단할 수는 없다는 점은 명확히 해야 해. 서버에서 검증하지 않는 전투 결과는 원칙적으로 위조 가능하므로, 추후 유료 재화를 도입하기 전 보안 강화를 별도로 진행하자.

# 9\. 관리자가 게임 데이터를 확인하는 화면

처음부터 대규모 게임사 수준의 운영 툴을 만들 필요는 없어.

초기에는 다음 다섯 가지 화면만 있어도 충분해.

**운영 현황**

전체 가입자 수, 일간 활성 이용자 수, 평균 스테이지 진행, 오류 발생 현황

**유저 관리**

UID로 유저 검색, 보유 재화·드래곤·스테이지 기록 확인, 문의 대응

**선물·보상 관리**

전체 선물 발송, 특정 유저 보상, 발송 이력, 중복 지급 확인

**이벤트·공지 관리**

출석 이벤트, 룰렛, 시작·종료 시각, 게임 공지

**설정·감사 로그**

운영자별 변경 기록, 보상 지급 로그, 이전 설정 복원

관리자 화면은 일반 게임 유저가 접근할 수 없는 별도 웹사이트로 만들고, 운영자 계정에는 강력한 인증을 적용하자.

**관리자 권한은 앱에 들어 있는 비밀번호나 비밀키로 확인하지 말고 서버에서 검증**해야 해. 또한 대량의 루비를 지급할 때는 발송 전 최종 확인을 거치고, 발송자·시각·대상·수량을 기록하도록 하자.

# Dragon Force — 신규 작업 및 계정·서버 시스템 설계 요청

기존 7단계 개발 완료 보고를 확인했습니다.

다음 작업인 로비 UI 개편, 행동력, 선물함 시스템 구현을 승인합니다. 여기에 선물함 일괄 수령과 미수령 보상 개수 표시를 추가해 주세요.

추가로 게임 운영을 위한 로그인·계정·클라우드 저장·전체 유저 보상 발송 시스템도 설계하고자 합니다.

## A. 기존 작업에 추가할 사항

### 1. 선물함 기능 추가

- 로비 선물함 아이콘에 미수령 보상 개수를 표시합니다.
- 선물함에 '모두 받기' 버튼을 추가합니다.
- 수령 가능한 선물은 한 번에 지급합니다.
- 행동력 상한 등으로 수령 불가능한 선물은 선물함에 남겨둡니다.
- 개별 수령과 일괄 수령 모두 지원합니다.
- 이미 수령한 보상은 중복 지급되지 않아야 합니다.
- 수령 성공 시 미수령 개수와 보유 재화를 즉시 갱신합니다.
- 수령 내역과 미수령 내역은 앱 종료 후에도 유지합니다.
- 전체 유저 보상, 이벤트 보상, 스테이지 보상 등을 같은 선물함에서 관리할 수 있도록 설계합니다.

기존 행동력 규칙은 유지합니다.

- 최대 행동력 40
- 30분마다 1 회복
- 스테이지 입장 시 5 소모
- 스테이지·난이도별 최초 클리어 시 행동력 20을 선물함으로 지급
- 행동력 20을 전부 수령할 공간이 없으면 선물함에 유지
- 행동력과 회복 시각 저장

### 2. 기존 UI 작업

- 로비·상점·장비·드래곤 화면을 기존 시안에 맞게 개선
- 소환 기능을 상점 탭으로 통합
- 기존 장비·스킬·드래곤 이미지 연결
- 저장 데이터 및 기존 기능 유지
- 다른 개발 세션과 동일 파일 동시 수정 방지

## B. 신규 계정 및 로그인 시스템 설계

### 1. 로그인 방식

추천 로그인 방식은 다음 세 가지입니다.

1. 게스트 플레이
2. Apple 로그인
3. Google 로그인

최초 실행 시 게스트로 즉시 플레이할 수 있도록 하고, 이후 설정 메뉴에서 Apple 또는 Google 계정을 연동할 수 있도록 설계합니다.

게스트가 계정을 연동할 때 기존 드래곤·장비·재화·스테이지 기록이 유지되어야 합니다.

로그인하지 않은 게스트도 내부 고유 UID를 부여받도록 합니다.

### 2. 백엔드 기술

Firebase 사용을 우선 검토해 주세요.

- Firebase Authentication: 계정 및 로그인
- Cloud Firestore: 유저 게임 데이터
- Cloud Functions: 보상 지급·재화 변경·검증
- Firebase Cloud Messaging: 푸시 알림
- Firebase App Check 및 보안 규칙: 비정상 접근 위험 감소

기존 프로젝트 구조 및 iOS 앱 구현 방식과의 호환성을 먼저 확인해 주세요.

### 3. 저장할 게임 데이터

- 유저 UID 및 닉네임
- 계정 연동 방식
- 드래곤 10종 보유 및 성장 정보
- 골드·루비·소환권
- 장비·특수 스킬·연구소
- 행동력 및 회복 시간
- 스테이지·난이도별 진행 기록
- 최초 클리어 보상 수령 기록
- 소환 천장 카운터
- 크리스마스 출석·룰렛 기록
- 선물함 및 수령 내역
- 저장 데이터 버전

개인정보는 운영에 필요한 최소한으로 수집하고, 계정 삭제 기능과 개인정보처리방침도 준비해 주세요.

### 4. 기존 로컬 저장 데이터 이전

기존 플레이어의 저장 데이터가 사라지지 않아야 합니다.

- 최초 서버 연동 시 기존 로컬 데이터 확인
- 신규 계정인 경우 검증 후 1회 이전
- 이미 서버에 데이터가 있으면 자동 덮어쓰기 금지
- 이전 성공 여부와 기록 저장
- 마이그레이션 과정에서 복사본 유지
- 계정 충돌 시 자동 재화 합산 금지

## C. 관리자 운영 시스템

개발자가 앱 업데이트 없이 전체 유저에게 선물이나 공지를 보낼 수 있도록 설계합니다.

### 1. 관리자 기능

- 전체 유저에게 루비·골드·행동력·소환권·드래곤 조각 지급
- 특정 UID 유저에게 보상 지급
- 이벤트 참여자 등 조건별 보상 지급
- 공지사항 작성·수정
- 이벤트 시작·종료 관리
- 보상 발송·수령 이력 조회
- 전체 유저 수 및 진행 현황 확인
- 게임 운영 설정 수정

### 2. 전체 보상 지급 방식

전체 유저 보상은 서버에 보상 캠페인으로 등록합니다.

유저가 게임에 접속하면 수령 대상인 캠페인을 확인하고 선물함에 표시합니다.

유저가 수령하면 서버에서 수령 여부를 확인하고 보상을 지급합니다.

- 동일 캠페인 보상은 계정당 1회 지급
- 서버에서 재화 지급
- 수령과 재화 지급은 원자적으로 처리
- 중복 요청 및 네트워크 재시도 시 중복 지급 방지
- 전체 보상 캠페인 식별자 및 발송 이력 저장
- 관리자 권한은 서버에서 검증
- 관리자는 별도 인증 및 감사 로그 적용

### 3. 게임 업데이트

게임 설정값과 이벤트 보상은 서버에서 변경할 수 있도록 설계합니다.

다만 신규 드래곤 이미지·새 전투 기능 등 클라이언트 자산이나 코드 수정이 필요한 경우에는 앱 업데이트를 사용합니다.

## D. 보안 및 데이터 관리

- 루비·골드·행동력·소환권 등 중요 재화는 서버를 최종 기준으로 관리
- 클라이언트에서 임의로 잔액을 수정해 서버에 반영할 수 없도록 구현
- 룰렛 추첨과 보상 지급은 서버에서 처리
- 스테이지 보상은 전투 세션 ID 및 정산 기록으로 중복 지급 방지
- 모든 중요 지급·차감 기록에 고유 작업 ID 부여
- 계정별 데이터 접근 권한 제한
- 관리자용 비밀키를 앱 코드에 포함하지 않음
- 계정 삭제 및 개인정보 처리 기능 준비
- 실패한 지급 요청을 안전하게 재시도할 수 있도록 구현

## E. 작업 우선순위

1. 현재 main 코드 확인 및 세션 간 수정 파일 충돌 방지
2. 기존 로비·상점·장비·드래곤 UI 개선
3. 행동력 및 선물함 저장 시스템
4. 미수령 개수 표시·개별 수령·일괄 수령
5. 기존 기능 전체 테스트
6. Firebase 연결 가능 여부 및 구현 구조 설계
7. 게스트·Apple·Google 로그인 설계
8. 기존 로컬 저장 데이터 마이그레이션
9. 클라우드 저장 및 서버 재화 검증
10. 전체 유저 보상 발송 및 관리자 시스템

**중요:** 1~5번은 이미 승인한 작업이므로 우선 진행해 주세요.

6~10번은 신규 설계 범위이므로 기존 앱의 구조, 개발 일정, iOS 심사 영향, Firebase 비용 및 배포 환경을 확인한 후 단계적으로 구현해 주세요.

App Store 제출 전에는 미완성 기능을 억지로 활성화하지 않고, 검증된 기능만 제공해 주세요.

완료 후에는 변경 파일, 테스트 결과, 클라우드 설정이 필요한 항목, 추가로 결정할 사항을 정리해 주세요.


## 12\. 최종 추천

현재 단계에서 나는 **게스트 플레이 + Apple 로그인 + Google 로그인 + Firebase + 선물함 + 운영자 보상 시스템**을 장기적인 기본 구조로 추천해.

다만 11월 21\~22일 출시 제출을 목표로 한다면, 로그인과 서버 운영 기능까지 급하게 모두 넣기보다는 **기존 전투·UI·행동력·선물함을 먼저 안정화한 뒤, 서버 계정 시스템은 별도의 통합 작업으로 진행**하는 것이 안전해.

그리고 서버 운영이 시작되면 무료 이용 범위와 별개로 Firebase 사용량에 따른 비용, 백업, 운영 계정 보안을 꾸준히 확인해야 해.

이 기획은 아직 **개발 8단계 v1.0 초안**으로 두고, 실제 코드 구조를 확인한 뒤 최종 확정하면 좋겠어.
