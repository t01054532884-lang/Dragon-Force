# 첫 출시에 루비 결제 · 로그인 넣기 — 계획 (2026-11-20 제작자 결정)

> 제작자 결정(2026-11-20): **첫 출시에 루비 현금 결제와 로그인을 넣는다**(상업적 성공 목표). 기존 계획(첫 출시는 결제·로그인 없음, `docs/STAGE8.md` 3절 업데이트 1~3)을 앞당긴다.
> 기획자 원칙(2026-11-20 1차 검토) "첫 제출에 불필요한 신규 시스템은 추가하지 않는다"와 부딪히므로 기획자에게도 이 결정을 공유한다.

## 0. 확정 (제작자 2026-11-20)
- 서버: **Firebase + RevenueCat**
- 로그인: **게스트(자동) + Sign in with Apple 연결**, 앱 안 계정 삭제
- 사업자등록: 아직 안 함 → 제작자 판단 "출시하고 등록". AI 안내(법률·세무 확정 아님, 세무사 확인 권장):
  - 애플 유료 앱 계약은 **개인 개발자 계정으로도** 맺을 수 있어(은행·세금 정보만) 사업자등록 없이 결제 출시 자체는 가능.
  - 다만 판매로 수입이 생기기 시작하면 부가가치세법상 **사업 개시일부터 20일 안에** 사업자등록을 해야 하고, 늦으면 미등록 가산세가 붙을 수 있음. 홈택스로 무료·보통 당일~며칠.
  - 그래서 **출시 직전~첫 매출 무렵에 등록**하는 일정이 안전. 통신판매업 신고 대상 여부는 관할 구청에 확인.

## 1. 첫 출시 범위 (제안)

| 영역 | 넣는 것 | 넣지 않는 것(이후) |
|---|---|---|
| 로그인 | **게스트(자동) + Sign in with Apple 연결**, 로그아웃, **앱 안 계정 삭제**(애플 심사 5.1.1(v) 필수) | Google 로그인(iOS만 먼저 내므로), 다른 기기 동시 접속 처리 |

| 루비 결제 | 애플 인앱결제(소모형 루비 묶음), **구매 복원 버튼**, 영수증 서버 검증 후에만 지급(거래 ID 1회), 결제 내역 | 구독, 패키지 상품, 광고 |
| 재화 보호 | 유료 루비 지급·소비는 서버 기록(거래 ID), 앱이 서버의 재화 값을 직접 바꾸지 못하게 | 전투 결과 전체 서버 검증(상한 검사만) |
| 법·정책 | 확률 공개(이미 있음), 결제 전 안내(청약철회·미성년자), 개인정보처리방침 개정, 이용약관 | — |

## 2. 구성 (제안)

- **Firebase**: Authentication(익명 → Apple 연결, 같은 UID 유지) · Cloud Firestore(`users/{uid}` 진행 저장) · Cloud Functions(루비 지급·소비, 계정 삭제). 지금 `Progress.ts`·`Mailbox.ts`의 순수 함수를 그대로 옮겨 쓰도록 이미 분리돼 있음.
- **RevenueCat**(결제 검증 서비스): 애플 영수증 검증·구매 복원을 대신 처리 → 서버(Functions)가 RevenueCat에 확인한 거래만 루비 지급. 직접 StoreKit 검증 서버를 만드는 것보다 빠르고 안전.
- 앱: Capacitor 플러그인(`@capacitor-firebase/authentication`, RevenueCat Capacitor SDK). 웹·데모에서는 결제 대신 "앱에서만 구매 가능" 표시.
- 비용: Firebase는 Functions를 쓰려면 **Blaze(사용한 만큼 요금)** 요금제 — 초기 규모는 무료 한도 안일 가능성이 큼, 예산 알림 설정. RevenueCat은 월 매출 $2,500까지 무료.

- 외부 설정(1~6)이 끝나야 실제 결제·로그인 시험이 가능. 사업자등록·통신판매업 신고는 보통 며칠, 애플 유료 앱 계약 승인도 며칠.
